অধ্যায় ০১

LLD রাউন্ড আসলে কী যাচাই করে

কোড লেখা নয় — দায়িত্ব ভাগ করা

LLD ইন্টারভিউয়ার একটাই জিনিস দেখতে চান: নতুন একটা প্রয়োজন এলে আপনার ডিজাইন কি ভাঙবে, নাকি বাড়বে? "পার্কিং লট ডিজাইন করুন" বলার ২০ মিনিট পর তিনি বলবেন — "এখন ইলেকট্রিক গাড়ির চার্জিং স্পট যোগ করুন"। আপনার ডিজাইনে যদি তখন পুরোনো ক্লাস কাটাছেঁড়া করতে হয়, আপনি হেরে গেলেন।

৪৫ মিনিটের কাঠামো

সময়কাজ
০–৫ মিনিটরিকোয়ারমেন্ট ও স্কোপ। "একাধিক ফ্লোর আছে? পেমেন্ট আছে? রিজার্ভেশন?"
৫–১২ মিনিটমূল entity চিহ্নিত করা — বিশেষ্যগুলো লিখে ফেলুন (Vehicle, Spot, Ticket, Floor)
১২–২৫ মিনিটক্লাস ডায়াগ্রাম — attribute, method, সম্পর্ক
২৫–৪০ মিনিটমূল ফ্লো-র কোড লেখা (সব ক্লাস নয়, ২–৩টা গুরুত্বপূর্ণ)
৪০–৪৫ মিনিটএক্সটেনশন প্রশ্ন, কনকারেন্সি, tradeoff

Entity বের করার সহজ কৌশল

রিকোয়ারমেন্ট বাক্যগুলো থেকে বিশেষ্য নিন — সেগুলো সম্ভাব্য ক্লাস। ক্রিয়া নিন — সেগুলো সম্ভাব্য মেথড। "একজন ব্যবহারকারী একটা গাড়ি নিয়ে পার্কিং লটে ঢুকে টিকিট নেয়" → User, Vehicle, ParkingLot, Ticket, আর মেথড issueTicket()। এটা নিখুঁত নয়, কিন্তু শূন্য থেকে শুরু করার সেরা উপায়, আর ইন্টারভিউয়ারের সামনে জোরে করলে ভালো দেখায়।

যে ভুলটা সবচেয়ে বেশি হয়

একটা ParkingLotManager ক্লাস বানিয়ে তাতে সব লজিক ঢেলে দেওয়া — গাড়ি খোঁজা, টাকা হিসাব, টিকিট ছাপা, ডেটাবেজে লেখা। একে বলে God object। ইন্টারভিউয়ার সাথে সাথে ধরে ফেলেন। প্রতিটা ক্লাসের একটাই কারণ থাকবে বদলানোর — এটাই পরের অধ্যায়ের প্রথম অক্ষর।

অধ্যায় ০২

SOLID

পাঁচটা নীতি — খারাপ ও ভালো কোড পাশাপাশি দেখুন

SOLID মুখস্থ বলতে পারা কোনো কৃতিত্ব নয়। কৃতিত্ব হলো — নিজের আঁকা ডিজাইনে কোন নীতিটা ভাঙছে সেটা নিজে ধরতে পারা। নিচে প্রতিটার জন্য আগে খারাপ কোডটা পড়ুন, তারপর টগল করুন।

নীতি
ইন্টারভিউতে কীভাবে ব্যবহার করবেন

নীতির নাম আওড়াবেন না। বরং সিদ্ধান্তের কারণ হিসেবে বলুন: "PaymentStrategy-কে ইন্টারফেস করছি, যাতে নতুন পেমেন্ট মাধ্যম যোগ করতে হলে পুরোনো কোনো ক্লাস ছুঁতে না হয় — শুধু নতুন একটা ক্লাস লিখলেই হবে।" এটাই Open/Closed, নাম না বলেই বলা হয়ে গেল।

অধ্যায় ০৩

ডিজাইন প্যাটার্ন

যেগুলো LLD ইন্টারভিউতে সত্যিই আসে

২৩টা GoF প্যাটার্ন মুখস্থ করার দরকার নেই। বাস্তব LLD ইন্টারভিউতে ঘুরেফিরে এই আটটাই আসে। প্রতিটার জন্য জানুন — কোন সমস্যা, কীভাবে সমাধান, আর কোন প্রবলেমে লাগে।

অতি-প্রয়োগের ফাঁদ

প্যাটার্ন শিখে ফেললে সবখানে লাগাতে ইচ্ছে করে। কিন্তু যেখানে if-else যথেষ্ট সেখানে Factory + Strategy + Observer বসালে ইন্টারভিউয়ার বিরক্ত হন — এটাকে বলে over-engineering, আর এটাও একটা লাল পতাকা। নিয়ম: প্যাটার্ন তখনই আনুন যখন পরিবর্তনের একটা বাস্তব দিক আছে।

অধ্যায় ০৪

ক্লাস ডায়াগ্রাম

চারটা সম্পর্ক — এগুলো গুলিয়ে ফেললে ডিজাইনটাই ভুল হয়ে যায়

সম্পর্কের ধরন
সবচেয়ে গুরুত্বপূর্ণ নিয়ম

Inheritance-এর চেয়ে Composition পছন্দ করুন। উত্তরাধিকার একটা শক্ত বাঁধন — সাবক্লাস প্যারেন্টের সব কিছু পায়, চাক না চাক, আর প্যারেন্ট বদলালে সব সাবক্লাস প্রভাবিত হয়। Composition-এ আপনি শুধু যা দরকার তা ভেতরে রাখেন, আর রানটাইমে বদলাতেও পারেন। ইন্টারভিউতে গভীর ক্লাস হায়ারার্কি (৩+ স্তর) আঁকলে প্রায় নিশ্চিতভাবে প্রশ্ন আসবে।

প্রবলেম ০১

Parking Lot

LLD-র "URL shortener" — সবচেয়ে জিজ্ঞাসিত

রিকোয়ারমেন্ট (যা জিজ্ঞেস করে বের করবেন)

  • একাধিক ফ্লোর, প্রতিটায় একাধিক স্পট
  • গাড়ির ধরন: মোটরসাইকেল, গাড়ি, ট্রাক — স্পটের আকারও তেমন
  • ঢোকার সময় টিকিট, বেরোনোর সময় সময়ভিত্তিক ফি
  • একাধিক এন্ট্রি/এক্সিট গেট, একাধিক পেমেন্ট পদ্ধতি
// স্পট খোঁজার কৌশলও ইন্টারফেস — নিকটতম, সবচেয়ে সস্তা, ফ্লোরভিত্তিক…
interface SpotAllocationStrategy {
    Optional<ParkingSpot> findSpot(List<ParkingFloor> floors, VehicleType type);
}

class ParkingLot {
    private final SpotAllocationStrategy allocator;
    private final PricingStrategy pricing;

    public Ticket park(Vehicle v) {
        ParkingSpot spot = allocator.findSpot(floors, v.getType())
            .orElseThrow(() -> new LotFullException());
        spot.occupy(v);
        return new Ticket(v, spot, Instant.now());
    }

    public Receipt unpark(Ticket t) {
        double fee = pricing.calculate(t);   // দাম কীভাবে হিসাব হয় ParkingLot জানে না
        t.getSpot().release();
        return new Receipt(t, fee);
    }
}

এক্সটেনশন প্রশ্নগুলো আগে থেকেই ভাবুন

  • "ইলেকট্রিক গাড়ির চার্জিং স্পট যোগ করুন।" → SpotType-এ নতুন মান + ElectricSpot যেটা ParkingSpot এক্সটেন্ড করে চার্জিং লজিক যোগ করে। কোনো পুরোনো ক্লাস বদলায় না।
  • "সপ্তাহান্তে ভিন্ন রেট।" → নতুন WeekendPricing ক্লাস, PricingStrategy ইমপ্লিমেন্ট। এজন্যই দামের হিসাব শুরু থেকেই ইন্টারফেসের পেছনে রাখা হয়েছিল।
  • "দুটো গাড়ি একই স্পট পেয়ে গেল।" → স্পট বরাদ্দ অ্যাটমিক হতে হবে; synchronized বা AtomicBoolean.compareAndSet()। অধ্যায় ০৯-এ বিস্তারিত।
প্রবলেম ০২

Elevator System

ফ্লোরে ক্লিক করুন — SCAN অ্যালগরিদম চলতে দেখুন

লিফটের আসল প্রশ্ন ক্লাস ডিজাইন নয়, শিডিউলিং। সবচেয়ে সরল উপায় হলো FCFS — যে আগে চেপেছে তার কাছে আগে যাও। কিন্তু ৫ তলা থেকে ১ তলায় নেমে আবার ৬ তলায় ওঠা অপচয়। বাস্তবে SCAN ব্যবহার হয় — এক দিকে যেতে যেতে পথে যত অনুরোধ আছে সব সেরে নেওয়া, তারপর ঘুরে দাঁড়ানো।

অবস্থা: IDLE · তলা ১
▲

যেকোনো তলায় ক্লিক করে অনুরোধ যোগ করুন — একসাথে কয়েকটা দিন

enum Direction { UP, DOWN, IDLE }

class Elevator {
    private int currentFloor;
    private Direction direction;
    private final TreeSet<Integer> up   = new TreeSet<>();          // ঊর্ধ্বমুখী অনুরোধ
    private final TreeSet<Integer> down = new TreeSet<>(reverseOrder()); // অধোমুখী
}

// একাধিক লিফট থাকলে কে যাবে সেটা আলাদা দায়িত্ব — তাই আলাদা ইন্টারফেস
interface ElevatorSelectionStrategy {
    Elevator select(List<Elevator> elevators, Request r);
}

দুটো TreeSet রাখাটাই মূল চাল — ঊর্ধ্বমুখী অনুরোধ অ্যারোহী ক্রমে, অধোমুখী অবরোহী ক্রমে। তখন "পরের গন্তব্য" মানে শুধু বর্তমান দিকের সেটের প্রথম উপাদান। সেট খালি হলে দিক উল্টে দিন। SCAN অ্যালগরিদম এভাবে কয়েক লাইনেই দাঁড়িয়ে যায় — আর এটা দেখাতে পারলে ইন্টারভিউয়ার খুশি হন।

যে পার্থক্যটা ধরতে হবে

দুই ধরনের অনুরোধ আছে: এক্সটার্নাল (ফ্লোরে দাঁড়িয়ে উপরে/নিচে বোতাম) আর ইন্টার্নাল (লিফটের ভেতরে তলা নম্বর)। এক্সটার্নাল অনুরোধে দিক জানা যায়, ইন্টার্নালে যায় না — এই পার্থক্যটা শিডিউলিং-এ কাজে লাগে। ইন্টারভিউতে এই দুটো আলাদা করতে পারলে বোঝা যায় আপনি সমস্যাটা সত্যিই ভেবেছেন।

Vending Machine

State প্যাটার্নের পাঠ্যপুস্তক উদাহরণ

ভেন্ডিং মেশিনের পুরো আচরণ নির্ভর করে সে কোন অবস্থায় আছে তার উপর। টাকা না দিয়ে আইটেম বাছা যাবে না; আইটেম না বেছে ডিসপেন্স হবে না। নিচে ভুল ক্রমে বোতাম চেপে দেখুন — মেশিন কীভাবে না বলে।

void selectItem(Item i) {
    if (state == IDLE) throw new Exception("আগে টাকা দিন");

// ভালো: প্রতিটা অবস্থা নিজের আচরণ নিজে জানে
interface VendingState {
    void insertCoin(VendingMachine m, int amount);
    void selectItem(VendingMachine m, Item item);
    void dispense(VendingMachine m);
}

class IdleState implements VendingState {
    public void insertCoin(VendingMachine m, int amt) {
        m.addBalance(amt);
        m.setState(new HasMoneyState());     // অবস্থা নিজেই পরের অবস্থা ঠিক করে
    }
    public void selectItem(VendingMachine m, Item i) {
        throw new IllegalStateException("আগে টাকা ঢোকান");
    }
    public void dispense(VendingMachine m) {
        throw new IllegalStateException("কিছু বাছা হয়নি");
    }
}

লাভটা স্পষ্ট: নতুন একটা অবস্থা (যেমন OutOfStockState বা MaintenanceState) যোগ করতে হলে শুধু নতুন একটা ক্লাস লিখুন — পুরোনো কোনো ক্লাসে হাত দিতে হবে না। এটাই Open/Closed নীতি বাস্তবে।

Splitwise

এখানে আসল চ্যালেঞ্জ ক্লাস নয়, ডেটা মডেল ও অ্যালগরিদম। প্রতিটা খরচে থাকে একজন পরিশোধকারী আর কয়েকজন অংশগ্রহণকারী, আর ভাগের নিয়ম আলাদা হতে পারে — সমান, নির্দিষ্ট অঙ্ক, শতাংশ, বা শেয়ার। এই নিয়মটাই SplitStrategy ইন্টারফেস।

interface SplitStrategy {
    Map<User, BigDecimal> split(BigDecimal total, List<User> participants, Object cfg);
}
// EqualSplit, ExactSplit, PercentSplit, ShareSplit

// ব্যালান্স: প্রতি জোড়ার জন্য নয় — প্রতি ইউজারের নিট অবস্থান রাখুন
Map<User, BigDecimal> netBalance;  // ধনাত্মক = পাবে, ঋণাত্মক = দেবে

"সবচেয়ে কম লেনদেনে হিসাব মেটানো" — এটা একটা ক্লাসিক ফলো-আপ। প্রতিটা ইউজারের নিট ব্যালান্স বের করে, তারপর সবচেয়ে বেশি পাওনাদারের সাথে সবচেয়ে বেশি দেনাদারকে বারবার মেলানো (গ্রিডি, হিপ দিয়ে)। এটা সবসময় সর্বোত্তম নয় (সমস্যাটা NP-hard), কিন্তু বাস্তবে যথেষ্ট ভালো — এই সীমাবদ্ধতাটা স্বীকার করে নেওয়াটাই ভালো উত্তর।

টাকার জন্য কখনো float বা double ব্যবহার করবেন না — 0.1 + 0.2 != 0.3। BigDecimal নিন, বা পয়সাকে পূর্ণসংখ্যা হিসেবে রাখুন। এই একটা কথা বললেই ইন্টারভিউয়ার বোঝেন আপনি বাস্তবে কোড লিখেছেন।

কনকারেন্সি

যে ফলো-আপ প্রশ্নটা প্রায় সবসময় আসে

২৫ মিনিট ডিজাইন করার পর ইন্টারভিউয়ার বলবেন — "দুজন একই সাথে শেষ স্পটটা চাইলে?" এটা ভলিউম ৩-এর টিকিট প্রবলেমের সেই একই সমস্যা, কিন্তু এবার এক প্রসেসের ভেতরে।

// ✕ ভাঙা: চেক ও দখলের মাঝখানে অন্য থ্রেড ঢুকে যেতে পারে
if (spot.isFree()) {      // থ্রেড A এখানে, থ্রেড Bও এখানে
    spot.occupy(vehicle);  // দুজনই দখল করে ফেলল
}

// ✓ সমাধান ১: অ্যাটমিক compare-and-set — লক ছাড়াই, দ্রুত
class ParkingSpot {
    private final AtomicBoolean free = new AtomicBoolean(true);
    public boolean tryOccupy(Vehicle v) {
        if (!free.compareAndSet(true, false)) return false;  // একজনই জেতে
        this.vehicle = v;
        return true;
    }
}

// ✓ সমাধান ২: কনকারেন্ট কালেকশন — খালি স্পটের কিউ
ConcurrentLinkedQueue<ParkingSpot> freeSpots;
ParkingSpot spot = freeSpots.poll();   // অ্যাটমিক — একটাই থ্রেড এটা পাবে
if (spot == null) throw new LotFullException();

যা বলতে পারলে আলাদা করে নজরে পড়বেন

  • লকের পরিধি ছোট রাখুন। পুরো ParkingLot অবজেক্টে synchronized দিলে সব গেট একটা লাইনে দাঁড়াবে। বদলে প্রতি ফ্লোরে বা প্রতি স্পটে লক দিন — সমান্তরালতা টিকে থাকে।
  • একাধিক লক নিলে সবসময় একই ক্রমে নিন — নাহলে deadlock। দুই থ্রেড যদি একজন A→B আর অন্যজন B→A ক্রমে লক নেয়, দুজনই চিরকাল অপেক্ষা করবে।
  • Immutable অবজেক্ট থ্রেড-সেফ, বিনা খরচে। Ticket-এর মতো ক্লাস তৈরির পর আর বদলায় না — সব ফিল্ড final করে দিন, তাহলে কোনো সিঙ্ক্রোনাইজেশনই লাগবে না। ডিজাইনে যত বেশি জিনিস immutable, তত কম কনকারেন্সি বাগ।
  • লকের চেয়ে অ্যাটমিক অপারেশন পছন্দ করুন — AtomicBoolean, ConcurrentHashMap.putIfAbsent(), ConcurrentLinkedQueue.poll()। এগুলো লক ছাড়াই সঠিকতা দেয় এবং দ্রুততর।
সংযোগটা লক্ষ করুন

এই অধ্যায়ের compareAndSet, ভলিউম ৩-এর SET seat NX, আর ভলিউম ২-এর অপ্টিমিস্টিক ভার্সন চেক — তিনটাই একই ধারণা, তিনটা ভিন্ন স্কেলে। থ্রেড, প্রসেস, বা ডেটাসেন্টার — যেখানেই দুজন একই সম্পদ চাইবে, সমাধান একটাই: চেক আর দখল যেন একটাই অবিভাজ্য পদক্ষেপ হয়। এই সংযোগটা ইন্টারভিউতে বলতে পারলে বোঝা যায় আপনি নিয়ম নয়, নীতি শিখেছেন।
